# u1. 객체의 실제 모양 — 모든 것은 PyObject다

## 지도 확인

00장에서 코드가 어떻게 실행되는지(바이트코드 → PVM → 프레임)를 봤다.
이제 그 위를 흐르는 **값**의 정체를 본다.
`LOAD_FAST`가 배열에서 꺼내는 그것, 값 스택에 올라가는 그것이 실제로 무엇인가.

이 유닛이 01장 전체의 토대다. 여기서 그린 그림 위에서
이름 바인딩(u2), `is`와 인터닝(u3), 인자 전달(u4)이 전부 설명된다.

## 개념 1 — 파이썬에 원시 타입은 없다

자바에는 두 종류가 있다.

```java
int x = 5;              // 원시 타입 — 값이 변수 자리에 직접 들어감
String s = "hi";        // 참조 타입 — 힙의 객체를 가리키는 주소가 들어감
```

**파이썬에는 원시 타입이 없다.** 정수 5도, 문자열도, 함수도, 클래스도,
`None`도 전부 힙에 있는 **객체**다. 예외 없다.

```python
(5).bit_length()        # 정수에 메서드가 있다 = 객체다
type(5)                 # <class 'int'>
isinstance(5, object)   # True
```

그래서 파이썬의 변수는 **항상** 객체를 가리킨다. 값을 직접 담는 경우가 없다.

## 개념 2 — 모든 객체의 머리에 붙어 있는 것

CPython에서 객체는 C 구조체다. 그리고 **모든 객체가 공통 헤더**로 시작한다.

```c
typedef struct _object {
    Py_ssize_t ob_refcnt;      // 참조 카운트 (8바이트)
    PyTypeObject *ob_type;     // 타입 객체 포인터 (8바이트)
} PyObject;
```

- `ob_refcnt` — **이 객체를 가리키는 이름/참조가 몇 개인가.** 0이 되면 즉시 해제된다.
- `ob_type` — **이 객체가 무슨 타입인가.** `type(x)`가 읽는 것이 이것이다.

64비트 환경에서 이 헤더만 **16바이트**다. 실제 데이터는 그 뒤에 붙는다.

```
정수 5 객체의 메모리
┌──────────────┬──────────────┬──────────────┐
│ ob_refcnt    │ ob_type      │ 실제 값 5     │
│ (8바이트)     │ → int 타입    │              │
└──────────────┴──────────────┴──────────────┘
       └────── 공통 헤더 ──────┘
```

확인:

```python
import sys
sys.getsizeof(5)        # 28 — 헤더 16 + 정수 데이터 12
sys.getsizeof(0)        # 28 — 값과 무관하게 같은 구조
sys.getsizeof(True)     # 28
```

자바의 `int`는 4바이트다. 파이썬 정수 하나가 28바이트인 이유가 이 헤더다.
"파이썬이 느린 세 겹" 중 **둘째 겹**(모든 값이 힙의 객체)의 실체가 이것이다.

## 개념 3 — id()는 메모리 주소다

객체가 힙에 있으니 주소가 있다. `id()`가 그 주소를 돌려준다.

```python
x = [1, 2]
id(x)                   # 예: 140234...  (CPython에서는 메모리 주소)
hex(id(x))              # 주소를 16진수로
```

**주의**: `id()`가 메모리 주소라는 건 **CPython 구현 디테일**이다.
언어 명세는 "객체의 수명 동안 유일한 정수"만 보장한다.
PyPy 등 다른 구현체에서는 주소가 아닐 수 있다.

그리고 **객체가 죽으면 그 주소는 재사용된다.** 그래서 이런 함정이 있다.

```python
id([1,2]) == id([3,4])   # True가 나올 수 있다!
                         # 첫 리스트가 즉시 죽고 그 자리에 두 번째가 생성됨
```

`id()` 비교는 두 객체가 **동시에 살아 있을 때만** 의미가 있다.

## 개념 4 — refcount: 몇 개가 나를 가리키나

`ob_refcnt`는 실시간으로 변한다. 관측할 수 있다.

```python
import sys
a = [1, 2, 3]
sys.getrefcount(a)      # 2 — a가 1개 + getrefcount의 인자로 1개(일시적)
b = a
sys.getrefcount(a)      # 3 — b도 같은 객체를 가리킴
del b
sys.getrefcount(a)      # 2
```

`sys.getrefcount()`가 항상 **1을 더해서** 보고하는 이유는,
함수를 호출하는 순간 인자로 넘기느라 참조가 하나 더 생기기 때문이다.
(u4에서 본 그림 — 값 스택에 올리고 프레임의 지역 변수에 담는 그 과정)

refcount가 0이 되면 객체는 **즉시** 해제된다. 이게 CPython의 기본 메모리 관리
방식이고, 20장(메모리와 GC)에서 순환 참조 문제와 함께 정식으로 다룬다.

## 개념 5 — 그래서 변수 안에는 뭐가 들어 있나

u3에서 배운 것과 합치면:

```
프레임의 지역 변수 배열
┌─────┬─────┬─────┐
│  0  │  1  │  2  │
└──┬──┴──┬──┴──┬──┘
   │     │     │      ← 각 칸에 들어 있는 것은 "값"이 아니라
   ↓     ↓     ↓         객체를 가리키는 **포인터**
 [객체] [객체] [객체]     (힙 어딘가)
```

`LOAD_FAST 0`이 배열에서 꺼내는 것도 포인터고,
값 스택에 올라가는 것도 포인터다. **파이썬 실행 내내 오가는 것은
객체 자체가 아니라 객체를 가리키는 화살표뿐이다.**

이 한 문장이 01장 나머지 전부의 전제다.

## 자바와 비교 — "절반은 같고 절반은 다르다"

**같은 것**: 자바의 참조 타입(`String`, 배열, 객체)은 파이썬과 똑같다.
변수에 주소가 들어가고, 힙에 객체가 있다.

**다른 것**: 자바는 원시 타입(`int`, `double`, `boolean`)이 따로 있어서
값이 변수 자리에 직접 들어간다. 파이썬은 그런 게 없다.

**결정적으로 다른 것**: 메모리 회수 방식.
- 자바: GC만 사용. 객체가 언제 죽는지 예측 불가
- CPython: **참조 카운팅이 기본** + 순환 참조용 GC 보조.
  refcount가 0이 되는 순간 즉시 해제 → 소멸 시점이 예측 가능

이 차이가 실무에서 드러나는 지점: 파이썬에서 `with` 없이 파일을 열어도
변수가 스코프를 벗어나면 대개 즉시 닫히는데, 자바는 그렇지 않다.
(그렇다고 `with`를 안 써도 된다는 뜻은 아니다 — 11장에서 다룬다.)

## 백엔드 관점

- **메모리 사용량 감각**: 정수 하나 28바이트, 빈 리스트 56바이트.
  100만 건 데이터를 dict 리스트로 들고 있으면 왜 수백 MB가 되는지 설명된다.
  17장(`__slots__`), 27장(memoryview)이 이 문제의 대응책이다.
- **refcount 이해가 메모리 누수 디버깅의 기초**다. "왜 이 객체가 안 죽지?"는
  "누가 아직 가리키고 있나?"와 같은 질문이다. 20장에서 `tracemalloc`,
  `gc.get_referrers()`로 실습한다.

## 실무 규칙

- `sys.getsizeof()`는 **객체 자신의 크기만** 잰다. 리스트의 경우 담긴 객체들의
  크기는 포함되지 않는다 (포인터 배열 크기만). 전체를 재려면 재귀 순회가 필요하다.
- `id()`로 객체 동일성을 판단할 땐 두 객체가 동시에 살아 있는지 확인할 것.

## 3문장 요약 (직접 작성)

1. 파이썬은 원시 자료형이 없다. 모든 자료형이 객체다.
2. 파이썬 객체는 ob_refcnt, ob_type 라는 헤더와 뒷부분으로 나뉘며 int와 같은 자료형은 실제값 부분에 값이 들어가지만 리스트는 값들의 주소만 들어간다.
3. 파이썬 객체를 참조하면 ob_refcnt가 늘어나며 ob_refcnt가 0이되면 객체는 소멸한다. 순환 참조와 같은 문제를 GC가 보조한다.
