# u2. 이름은 상자가 아니라 화살표다

## 지도 확인

u1에서 "파이썬에서 오가는 건 객체가 아니라 포인터(화살표)"라고 했다.
그 화살표를 **객체 쪽**에서 본 게 refcount였다면, 이번엔 **이름 쪽**에서 본다.
`x = 5`가 실제로 무슨 일을 하는지, `b = a`가 왜 복사가 아닌지.
여기가 01장에서 자바 감각을 가장 세게 깨야 하는 지점이다.

## 개념 1 — 자바의 상자, 파이썬의 화살표

**자바**에서 변수는 값을 담는 **상자**다.

```java
int x = 5;        // x라는 상자 안에 5가 들어감
int y = x;        // y라는 새 상자에 5를 복사
y = 10;           // y 상자만 바뀜, x는 5 그대로
```

**파이썬**에서 이름은 객체에 붙인 **꼬리표(화살표)**다.

```python
x = 5             # 5 객체를 만들고, x라는 화살표를 그 객체에 붙임
y = x             # y라는 화살표를 "같은 객체"에 붙임 (복사 아님!)
y = 10            # y 화살표를 10 객체로 옮김. x는 5를 계속 가리킴
```

결과는 같아 보이지만(`x`가 5로 남음) **일어난 일이 다르다.**
자바는 5를 복사했고, 파이썬은 화살표를 옮겼다.
이 차이가 리스트 같은 가변 객체에서 드러난다.

## 개념 2 — `=`는 "담다"가 아니라 "가리키다"

파이썬의 `x = 어떤것`은 항상 이 순서다.

1. 오른쪽 `어떤것`을 평가해서 **객체**를 얻는다 (없으면 만든다)
2. 왼쪽 이름 `x`를 그 객체에 **바인딩**(화살표 연결)한다

u2에서 `def`가 "함수 객체를 만들어 이름에 바인딩"이라 했던 그 바인딩과
**완전히 같은 동작**이다. `def f(): ...`도 `f = <함수객체>`였다.

```python
x = [1, 2, 3]     # 리스트 객체 생성 → x가 가리킴
x = "hello"       # 문자열 객체 생성 → x를 그리로 옮김
                  # (리스트는 이제 아무도 안 가리킴 → refcount 0 → 소멸)
```

## 개념 3 — b = a 는 복사가 아니다

```python
a = [1, 2, 3]
b = a             # 화살표만 복사. 리스트는 여전히 하나
```

```
   a ──┐
       ├──→ [1, 2, 3]     객체 1개, 화살표 2개
   b ──┘
```

같은 객체를 둘이 가리키니, 한쪽으로 바꾸면 다른 쪽에도 보인다.

```python
b.append(4)
print(a)          # [1, 2, 3, 4]  ← a로 봐도 바뀌어 있음
print(a is b)     # True — 같은 객체
```

이게 u1에서 본 refcount 증가의 정체다. 화살표가 2개니 refcount가 2.

## 개념 4 — 재대입 vs 변경 (제일 중요)

두 가지를 반드시 구분해야 한다.

**재대입 (rebinding)** — 이름의 화살표를 **다른 객체로 옮김**
```python
a = [1, 2, 3]
b = a
b = [9, 9]        # b의 화살표만 새 객체로. a는 원본 그대로
print(a)          # [1, 2, 3]
```
```
   a ──→ [1, 2, 3]
   b ──→ [9, 9]        이제 서로 다른 객체
```

**변경 (mutation)** — 화살표가 가리키는 **객체 내용을 바꿈**
```python
a = [1, 2, 3]
b = a
b.append(4)       # 객체 자체를 수정. a도 같은 걸 보니 영향받음
print(a)          # [1, 2, 3, 4]
```

**핵심**: `b = ...`는 항상 재대입(화살표 옮기기)이고,
`b.append()`, `b[0] = ...`, `b.attr = ...`는 변경(객체 수정)이다.
`=`의 왼쪽이 그냥 이름이면 재대입, `b[0]`이나 `b.x`면 변경이다.

이 구분이 06장(가변성과 복사) 전체의 씨앗이다.

## 개념 5 — 네임스페이스는 dict다

"이름을 객체에 바인딩한다"의 실체는 **dict에 키-값을 넣는 것**이다.
전역 이름은 모듈의 dict에, 지역 이름은 프레임에 저장된다(u3, u4).

```python
x = 5
globals()["x"]        # 5 — 전역 네임스페이스는 진짜 dict
```

`x = 5`는 개념적으로 `globals()["x"] = <5 객체>`와 같다.
그래서 u1에서 "dict 값 자리에 든 건 포인터"라고 한 것이다 —
네임스페이스가 이름(문자열) → 객체(포인터) 매핑이기 때문이다.

이 사실이 08장(dict 내부)과 07장(스코프)으로 이어진다.

## 자바와 비교 — 정리

| | 자바 | 파이썬 |
|---|---|---|
| 변수 = | 값을 담는 상자 (원시) 또는 참조 | 객체에 붙은 꼬리표 |
| `y = x` | 원시면 값 복사, 참조면 주소 복사 | 항상 화살표 복사 |
| `int` 같은 값 | 상자에 직접 | 객체를 가리킴 (원시 없음) |
| 원본 보호 | 원시 타입은 자동으로 안전 | 가변 객체는 공유되니 주의 |

자바에서 `int y = x; y = 10`이 x를 안 건드리는 건 **값을 복사**했기 때문이고,
파이썬에서 `y = x; y = 10`이 x를 안 건드리는 건 **화살표를 옮겼기** 때문이다.
같은 결과, 다른 메커니즘.

## 백엔드 관점

- 함수에 리스트/dict를 넘기면 **화살표가 복사되어** 함수 안에서 수정하면
  바깥도 바뀐다. 이게 의도치 않은 부작용의 흔한 원인이다 (u4에서 다룸).
- 캐시나 기본 설정 dict를 여러 곳에서 공유할 때, 한 곳에서 `.update()` 하면
  전부 바뀐다. "복사한 줄 알았는데 같은 객체였다" 버그의 뿌리.
- 진짜 복사가 필요하면 명시적으로 해야 한다 (`list(x)`, `dict(x)`, `copy` 모듈).
  06장에서 얕은/깊은 복사로 정식화한다.

## 실무 규칙

- `=`는 절대 복사하지 않는다. 복사가 필요하면 명시적으로.
- 함수 기본 인자로 가변 객체를 쓰지 않는다 (`def f(x=[])` 함정 — u2/00장에서 봤다).
  화살표 하나를 계속 재사용하기 때문이다.
