# u3. is vs == 와 인터닝 — 왜 5는 공유되고 리스트는 안 되나

## 지도 확인

u2에서 `a = [1,2,3]; c = [1,2,3]`은 서로 다른 객체라 `a is c`가 False였다.
그런데 `a = 5; c = 5`로 하면 `a is c`가 **True**다. 같은 5인데 왜?
이 유닛은 `is`와 `==`의 차이, 그리고 파이썬이 어떤 객체를 몰래 재사용하는지를 본다.

## 개념 1 — is 와 == 는 다른 질문이다

```python
a is b       # 같은 객체인가?  (화살표 두 개가 같은 곳을 가리키나)
a == b       # 같은 값인가?    (내용이 같나)
```

- `is` → **정체성(identity)**. `id(a) == id(b)`와 같다. 주소 비교.
- `==` → **동등성(equality)**. 객체의 `__eq__` 메서드를 호출해 내용 비교.

```python
a = [1, 2, 3]
b = a
c = [1, 2, 3]

a is b    # True  — 같은 객체
a is c    # False — 다른 객체
a == c    # True  — 내용은 같음
```

`==`가 어떻게 비교할지는 객체가 정한다. 리스트는 원소를 하나씩 비교하고,
사용자 클래스는 `__eq__`를 정의하지 않으면 기본이 `is`와 같아진다 (09장에서).

## 개념 2 — 그런데 작은 정수는 is도 True다

```python
a = 5
c = 5
a is c        # True !  — 리스트와 다르다
```

리스트는 매번 새 객체인데 정수 5는 왜 같은 객체일까?

CPython은 **자주 쓰이는 작은 정수(-5 ~ 256)를 인터프리터 시작 시 미리 만들어
두고 재사용**한다. `5`라고 쓸 때마다 새로 만들지 않고, 미리 만든 그 하나를
가리킨다. 이걸 **인터닝(interning)** 또는 캐싱이라 한다.

```python
a = 256
c = 256
a is c        # True  — 캐시 범위 안

a = 257
c = 257
a is c        # False — 캐시 범위 밖! 각각 새로 만듦
```

**왜?** u1에서 봤듯 객체 하나에 헤더 16바이트 + 할당 비용이 든다.
`0`, `1`, `-1` 같은 건 프로그램에서 수없이 쓰이니, 매번 만들면 낭비다.
그래서 미리 만들어 공유한다. 256까지인 건 그냥 CPython이 정한 경계다.

## 개념 3 — 문자열도 인터닝된다 (일부)

```python
a = "hello"
c = "hello"
a is c        # True (보통) — 짧은/식별자 같은 문자열은 인터닝됨

a = "hello world!"
c = "hello world!"
a is c        # 상황에 따라 다름 — 공백/특수문자 있으면 인터닝 안 될 수 있음
```

파이썬은 **식별자처럼 생긴 문자열**(변수명이 될 수 있는 것)을 자동 인터닝한다.
소스 코드에 등장하는 이름들(`co_names`, `co_varnames`)이 전부 문자열이고,
이걸 dict 키로 계속 조회하니(u3/00장) 같은 문자열을 재사용하는 게 이득이다.

**중요**: 이 동작은 **CPython 구현 디테일**이고 버전·상황에 따라 다르다.
절대 여기 의존한 코드를 짜면 안 된다.

## 개념 4 — 그래서 규칙: 값 비교는 무조건 ==

인터닝은 최적화일 뿐, **언제 되는지 보장되지 않는다.**
그래서 값을 비교할 때 `is`를 쓰면 언젠가 터진다.

```python
x = 1000
if x is 1000:     # 위험! 257 이상은 캐시 안 되니 False일 수 있음
    ...
if x == 1000:     # 올바름
    ...
```

파이썬 3.8+는 `is`로 리터럴을 비교하면 **SyntaxWarning**을 낸다.
"너 아마 ==를 쓰려던 거지?"라고 알려주는 것이다.

## 개념 5 — is 를 써야 하는 곳

`is`는 **정체성이 중요한 특수한 것들**에만 쓴다. 대표적으로 `None`.

```python
if x is None:        # 올바름 — None은 프로그램에 딱 하나뿐인 객체
if x == None:        # 동작은 하지만 관례 위반. __eq__가 오버라이드됐으면 위험

if x is True:        # 보통 불필요. if x: 로 충분한 경우가 많음
```

`None`, `True`, `False`는 각각 **싱글턴**이다 — 프로그램 전체에서 객체가
하나뿐이라 `is` 비교가 안전하고 빠르다. u1의 refcount로 보면,
`None`은 어디서나 가리켜서 refcount가 수천이다.

정리하면:
- **값이 같은지** → `==`
- **바로 그 객체인지** (None, 싱글턴, 캐시 검사) → `is`

## 자바와 비교 — 거의 판박이다

이 주제는 자바와 **놀랍도록 같다.**

```java
Integer a = 127, b = 127;
a == b;              // true  — 자바도 -128~127을 캐시함! (Integer 캐시)
Integer c = 128, d = 128;
c == d;              // false — 캐시 밖

String s1 = "hi", s2 = "hi";
s1 == s2;            // true  — 자바도 문자열 리터럴을 인터닝 (String pool)
s1.equals(s2);       // 항상 값 비교 — 파이썬의 ==
```

대응 관계:
- 자바 `==` (참조 비교) = 파이썬 `is`
- 자바 `.equals()` = 파이썬 `==`
- 자바 Integer 캐시(-128~127) = 파이썬 작은 정수 캐시(-5~256)
- 자바 String pool = 파이썬 문자열 인터닝

자바에서 "Integer는 ==로 비교하지 마라, equals 써라"라고 배운 그 이유가
파이썬 "값은 is 말고 == 써라"와 **정확히 같은 문제**다. 범위 숫자만 다르다.

## 백엔드 관점

- `if status == None` 같은 코드는 리뷰에서 `is None`으로 지적받는다. 관례다.
- ORM 객체나 캐시에서 "같은 레코드인가"를 판단할 때 `is`(같은 인스턴스)와
  `==`(같은 값/PK)를 구분해야 한다. `==`를 어떻게 정의하느냐가 09장 주제.
- 인터닝에 의존한 코드는 파이썬 버전 올리면 깨진다. 절대 금지.

## 실무 규칙

- 값 비교는 `==`, 싱글턴(None 등) 비교는 `is`. 예외 없다.
- `is`로 리터럴 비교하지 않는다 (SyntaxWarning이 경고해준다).
- `x is None`은 관례이자 안전. `x == None`은 쓰지 않는다.

## 3문장 요약 (직접 작성)

1. 파이썬에서 is는 identity, 정체성, 같은 객체인지를 판단하고 ==는 equlity, 동등성 값이 같은지를 판단한다.
2. 파이썬에서는 자주쓰는 값(작은 정수, 문자열)들은 객체를 재활용해서 사용하는 interning, 인터닝 기법을 사용한다.
3. 인터닝 기법때문에 is는 종종 예상과는 다른 결과를 낼수 있으며 == 연산도 내부적으로 __eq__를 오버라이드 할수있는 경우가 있기때문에 주의해야한다.
