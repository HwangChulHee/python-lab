# u1. 파이썬은 컴파일 언어다 (절반쯤은)

## 질문

"파이썬은 인터프리터 언어라서 컴파일을 안 한다" — 맞는 말인가?
그럼 `__pycache__` 안의 `.pyc` 파일은 뭔가?

## 개념

파이썬 코드는 실행 전에 **컴파일된다.** 다만 기계어가 아니라
**바이트코드**라는 중간 언어로 컴파일된다.

```
소스 코드 (.py)
   ↓ ① 토큰화        "def", "f", "(" 같은 단위로 쪼갬
   ↓ ② 파싱          문법 구조를 트리(AST)로 만듦
   ↓ ③ 컴파일        AST → 바이트코드
바이트코드            (임포트된 모듈이면 .pyc로 캐시)
   ↓ ④ 실행          파이썬 가상머신(PVM)이 한 명령씩 해석
결과
```

- **CPython**: 우리가 쓰는 파이썬의 공식 구현체. C로 작성. ①~④ 전부 수행.
- **PVM**: 바이트코드를 하나씩 읽어 실행하는 거대한 루프 (CPython 소스의 `ceval.c`).

정확한 문장: **"파이썬은 바이트코드로 컴파일된 뒤, 그 바이트코드가
가상머신에서 해석 실행된다."** 자바(소스 → 바이트코드 → JVM)와 같은 구조다.

## .pyc의 정체

컴파일(①~③)도 비용이라, 파이썬은 **임포트되는 모듈**의 바이트코드를
`__pycache__/모듈명.cpython-312.pyc`에 캐시한다.
소스가 안 바뀌었으면 다음 임포트 때 컴파일을 건너뛴다.

흔한 오해 두 가지:

1. `.pyc`는 **실행 속도**와 무관하다. **임포트(시작) 속도**만 빨라진다.
   어차피 실행되는 바이트코드는 동일하다.
2. 직접 실행한 스크립트(`python main.py`)는 `.pyc`가 안 생긴다.
   임포트된 모듈만 캐시된다.

## 백엔드 관점

"파이썬이 느리다"의 실체는 (1) 바이트코드 해석 오버헤드,
(2) 모든 값이 힙의 객체, (3) 타입이 런타임 결정 — 이 세 겹이다.
그러나 웹 서버 응답 시간의 지배 요인은 대부분 DB/외부 API 대기(IO)라서,
IO-bound 서비스에서는 언어 속도가 병목이 아니다.
CPU-bound 작업이 끼는 순간 이 느림이 그대로 노출된다.
→ 이 구분이 20장(GIL)~23장(asyncio)의 전제가 된다.
