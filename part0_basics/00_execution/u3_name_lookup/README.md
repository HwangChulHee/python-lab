# u3. 이름을 찾는 세 가지 방법 — LOAD_FAST vs LOAD_GLOBAL

## 지도 확인

u4에서 프레임 안에 **지역 변수 배열**이 있고 `LOAD_FAST`가 인덱스로 접근한다고 했다.
그런데 전역 변수와 속성은 그 배열에 없다. 그럼 어디서 어떻게 찾는가?
이번 유닛은 **이름 → 값**을 찾아내는 세 가지 경로를 비교하고, 그 비용을 실측한다.
00장의 마지막 유닛이다.

## 개념 1 — 세 가지 조회 경로

파이썬에서 이름을 쓰는 방법은 크게 셋이고, 바이트코드도 셋으로 나뉜다.

| 명령 | 무엇을 찾나 | 어디서 | 방식 |
|---|---|---|---|
| `LOAD_FAST` | 지역 변수 | 프레임의 배열 | **인덱스** 접근 |
| `LOAD_GLOBAL` | 전역/내장 | 모듈 dict → 내장 dict | **이름(문자열) 해시 조회** |
| `LOAD_ATTR` | 속성 | 객체의 `__dict__`, 클래스 등 | **이름 해시 조회 + 탐색** |

핵심 차이는 **언제 위치가 정해지느냐**다.

- 지역 변수: **컴파일 시점**에 `a → 0번`으로 확정 → 실행 시 배열 `[0]`
- 전역/속성: 컴파일 시점엔 이름 문자열만 남음 → 실행 시 dict에서 검색

## 개념 2 — 왜 전역은 인덱스로 못 바꾸나

컴파일러는 함수 본문만 보면 지역 변수가 뭐뭐인지 **전부** 알 수 있다.
대입되는 이름을 모으면 끝이고, 실행 중에 늘어나지 않는다.
그래서 미리 번호를 매길 수 있다 (`co_varnames`).

전역은 다르다. 모듈 네임스페이스는 실행 중에 얼마든지 바뀐다.

```python
globals()["새이름"] = 1      # 실행 중에 전역이 추가됨
del globals()["기존이름"]     # 삭제도 됨
```

무엇이 언제 생길지 컴파일 시점에 알 수 없으니 **위치를 확정할 수 없다.**
그래서 이름 문자열을 그대로 두고(`co_names`), 실행할 때마다 dict를 뒤진다.

`LOAD_FAST`의 FAST가 이 뜻이다 — **찾는 게 아니라 이미 아는 자리로 가는 것.**

## 개념 3 — LOAD_GLOBAL은 두 번 뒤진다

전역 이름을 찾을 때 순서가 있다.

1. **모듈 전역 dict** (`globals()`)
2. 없으면 **내장 dict** (`builtins`)

`len`, `print`, `range` 같은 내장 함수는 2번에서 발견된다.
즉 **내장 함수 호출은 dict 조회를 두 번** 한다는 뜻이다.
핫 루프에서 `len`을 지역에 바인딩하는 관용구가 있는 이유가 이것이다.

```python
def f(items):
    _len = len          # 여기서 한 번만 조회
    for x in items:
        _len(x)         # 이후로는 LOAD_FAST
```

## 개념 4 — 이름 조회 비용의 순서

```
LOAD_FAST     배열 인덱싱                        가장 빠름
LOAD_GLOBAL   dict 조회 1~2회
LOAD_ATTR     dict 조회 + 타입 탐색(MRO 등)      가장 느림
```

`math.sqrt(x)`를 루프에서 부르면 매 반복마다
`LOAD_GLOBAL math`(dict) + `LOAD_ATTR sqrt`(dict+탐색)가 일어난다.
루프 밖에서 `sqrt = math.sqrt`로 지역에 담으면 둘 다 `LOAD_FAST` 하나로 줄어든다.

**단, 이건 마이크로 최적화다.** 실측해서 몇 %인지 눈으로 확인하는 것이
이 유닛의 목적이지, 이렇게 코딩하라는 게 아니다.

## 자바와 비교 — "비슷해 보이지만 다르다"

자바는 지역 변수든 필드든 **전부 컴파일 시점에 위치가 확정**된다.
지역 변수는 슬롯 번호, 필드는 오프셋. 실행 중에 클래스에 필드가
추가되지 않기 때문이다.

파이썬은 지역 변수만 그렇고, 전역과 속성은 **실행 중에 이름으로 찾는다.**
객체에 속성을 마음대로 추가할 수 있는 유연성의 대가다.

```python
obj.new_attr = 1      # 파이썬: 언제든 가능
                      # 자바: 불가능 (컴파일 시 필드 확정)
```

이 유연성이 파이썬을 느리게 만드는 원인 중 하나이며,
동시에 ORM·모킹·플러그인 같은 것을 가능하게 하는 원천이다. (→ 15장)

## 백엔드 관점

- 요청당 수만 번 도는 루프가 아닌 이상 이름 조회 최적화는 의미 없다.
  응답 시간의 지배 요인은 여전히 DB·네트워크 IO다 (u1에서 본 구분).
- 다만 **왜 차이가 나는지 설명할 수 있는 것**은 다른 문제다.
  "지역 변수가 빠르다"를 아는 사람은 많고, "컴파일 시점에 인덱스가
  확정되니까"를 말할 수 있는 사람은 적다.
- dict 조회가 병목이라는 사실은 08장(dict와 해시 내부)으로 이어진다.
  해시 조회가 O(1)인데도 배열 인덱싱보다 느린 이유가 거기서 밝혀진다.

## 실무 규칙

- **측정 없이 최적화하지 않는다.** 이 유닛에서 `timeit`으로 직접 재는 것이
  그 습관의 시작이다. 계측 도구 전반은 27장에서 정리한다.
- 핫 루프에서만 지역 바인딩을 고려한다. 그 외에는 가독성이 우선이다.

## 3문장 요약 (직접 작성)

1. 컴파일 시점에 어떤 이름이 지역 변수인지가 확정되고, 지역은 인덱스로 박힌다. 전역과 속성은 이름만 남아 실행 시점에 조회된다.
2. 지역 < 전역 < 속성 순으로 느리지만, 3.11+ adaptive interpreter가 반복 실행되는 LOAD_GLOBAL을 특화해서 실측 차이는 1.1~1.3배에 그친다.
3. 막상 실무에서는 큰 병목은 아니기 때문에 최적화해서 코드를 작성할 필요는 없다.
