# u4. PVM은 스택 머신이다 — 전체 지도를 먼저 그린다

## 지도 확인

u1에서 "바이트코드를 PVM이 해석 실행한다"고 했고, u2에서 그 바이트코드에
`MAKE_FUNCTION`, `STORE_FAST` 같은 명령이 있는 걸 봤다. 그런데 이 명령들이
값을 "어디에" 올리고 "어디서" 꺼내는지는 아직 비어 있다. 이번 유닛이 그 빈칸
— **PVM의 내부 구조** — 를 채운다. 이 그림이 완성되면 이후 모든 장(클로저,
제너레이터, 예외, asyncio)은 이 그림에 부품을 하나씩 추가하는 작업이 된다.

## 개념 1 — 값 스택

PVM은 **스택 머신**이다. 모든 계산이 **값 스택(value stack)** 하나를 중심으로 돈다.

- `LOAD_*` = 값을 스택 **위에 올린다** (push)
- 연산/호출 = 스택 위에서 필요한 만큼 **꺼내서**(pop) 계산하고, 결과를 **다시 올린다**
- `STORE_*` = 스택 맨 위 값을 꺼내 이름에 저장한다

`x = a + b`를 손으로 트레이스하면:

```
바이트코드           스택 상태 (오른쪽이 위)
─────────────────────────────────────
LOAD_FAST a          [a값]
LOAD_FAST b          [a값, b값]
BINARY_OP +          [a+b]          ← 두 개 꺼내 더하고 결과를 올림
STORE_FAST x         []             ← 맨 위를 꺼내 x에 저장
```

함수 호출 `len("ab")`은 (전역 함수):

```
LOAD_GLOBAL len      [NULL, len]     ← LOAD_GLOBAL이 NULL까지 함께 민다
LOAD_CONST "ab"      [NULL, len, "ab"]
CALL 1               [반환값]
```

지역 변수에 담긴 함수를 부를 땐 `PUSH_NULL`이 따로 나온다:

```
PUSH_NULL            [NULL]
LOAD_FAST add        [NULL, add]
...
```

NULL을 까는 방법이 둘인 이유는 `LOAD_GLOBAL`이 인자 비트로 NULL 밀기를
겸할 수 있어 명령 하나를 아끼기 때문이다(전역 함수 호출이 흔해서).
`LOAD_FAST`엔 그 비트가 없어 `PUSH_NULL`을 따로 쓴다.

CALL 뒤의 숫자는 **괄호 안에 쓴 인자 개수**다. CALL은 실제로는
그 숫자만큼(인자) + 2칸을 더 꺼낸다. 왜 2칸인지는 개념 4에서.

## 개념 2 — 왜 하필 스택 머신인가

기계에게 계산을 시키는 방식은 크게 둘이다.

**레지스터 머신** (실제 CPU)
```
ADD R3, R1, R2     ← 피연산자 위치를 명령이 직접 지정
```

**스택 머신** (CPython, JVM)
```
LOAD a / LOAD b / ADD    ← 피연산자는 항상 "스택 맨 위 두 개"로 암묵 지정
```

스택 머신 명령은 **피연산자 주소를 안 적어도 된다.** 명령이 단순해지고,
컴파일러가 레지스터 할당이라는 어려운 문제를 풀 필요가 없다.
인터프리터를 단순하게 유지하려는 CPython의 선택이다.

대가는 명령 개수다. `a + b`가 레지스터 머신은 1개, 스택 머신은 3개.
명령 하나마다 평가 루프가 한 바퀴 도니 이게 곧 해석 오버헤드다.
u1에서 말한 "파이썬이 느린 세 겹" 중 첫째 겹의 실체가 이것이다.

## 개념 3 — 프레임: 함수 호출마다 생기는 작업 공간

값 스택은 전역에 하나가 아니다. **함수 호출마다 프레임(frame)이 새로 만들어지고,
프레임마다 자기만의 값 스택과 지역 변수 공간을 갖는다.**

프레임에 들어 있는 것:
- 실행 중인 코드 객체 참조 (어느 악보를 연주 중인가)
- 지역 변수 배열 (`LOAD_FAST`가 인덱스로 바로 접근하는 곳)
- 값 스택
- 현재 실행 위치 ip (몇 번째 명령까지 했나)
- **호출자의 프레임 링크** (누가 나를 불렀나)

`main() → f() → g()`처럼 호출이 겹치면 프레임이 사슬로 쌓인다.
이 사슬이 **콜 스택**이고, **트레이스백은 이 사슬을 출력한 것**이다.
`Traceback (most recent call last)` — 프레임 체인을 바깥에서 안쪽으로 읽어준 것.

이름 셋 혼동 주의:
- **값 스택**: 프레임 안에서 계산에 쓰는 작은 스택
- **콜 스택**: 프레임들이 쌓인 사슬
- 코드 객체 / 함수 객체 / **프레임** = 악보 / 연주자 / **연주 1회의 무대**

| 언제 만들어지나 | 무엇이 | 몇 개 |
|---|---|---|
| 컴파일 시점 | 코드 객체 | 함수 본문당 1개 |
| `def` 실행 시점 | 함수 객체 | `def`가 실행될 때마다 |
| **함수 호출 시점** | **프레임** | **호출할 때마다** |

u2 유제 2의 코드로 세어 보면:

```python
def factory(n):
    def multiply(x):
        return x * n
    return multiply

double = factory(2)
triple = factory(3)
```

| | 코드 객체 | 함수 객체 | 프레임 |
|---|---|---|---|
| `factory` | 1 | 1 (`def factory` 실행 시) | 2 (호출 2번, 반환하며 소멸) |
| `multiply` | 1 (공유) | 2 (`double`, `triple`) | 0 (아직 호출 안 함) |

그 뒤 `double(5)`를 백 번 부르면 함수 객체는 여전히 1개, 프레임만 100개 생겼다 사라진다.

세는 규칙:
- **코드 객체** = 소스에 `def`가 몇 번 쓰여 있나
- **함수 객체** = 그 `def` 줄이 몇 번 실행됐나
- **프레임** = 그 함수가 몇 번 호출됐나 (반환하면 소멸)

## 개념 4 — 인자 아래의 두 칸

함수 호출 시 스택은 항상 이 모양이다.

```
   인자들       ← 괄호 안에 쓴 것
   ─────
   두 칸        ← 함수와 그 짝꿍
```

아래 두 칸의 배치가 경우에 따라 **뒤집힌다.**

**일반 함수 호출** `add(1, 2)`
```
PUSH_NULL          NULL
LOAD_FAST add      NULL, add
LOAD_CONST 1       NULL, add, 1
LOAD_CONST 2       NULL, add, 1, 2
CALL 2
```
```
   2
   1        ← 인자
   add      ← 함수      ┐ 두 칸
   NULL     ← 빈 표시   ┘
```

**메서드 호출** `d.bark(3)`
```
LOAD_FAST d        d
LOAD_ATTR bark     bark, d      ← d를 꺼내 bark를 깔고 d를 그 위에
LOAD_CONST 3       bark, d, 3
CALL 1
```
```
   3        ← 인자
   d        ← self     ┐ 두 칸
   bark     ← 함수     ┘
```

**CALL이 구분하는 법**: 두 칸을 꺼내서 **아래 칸만 본다.**
- 아래가 NULL → 일반 호출. 위 칸이 함수.
- 아래가 값 → 아래가 함수, 위 칸이 첫 인자.

그래서 `d.bark(3)`은 `CALL 1`인데도 최종적으로 `bark(d, 3)`이 된다
(self는 카운트에 안 들어간다).

**왜 이렇게 설계했나**: 이 규약 덕에 일반 호출과 메서드 호출을
**같은 CALL 명령 하나로** 처리한다. 3.11까지 있던 `LOAD_METHOD`가
3.12에서 `LOAD_ATTR` 변형으로 흡수된 것도 같은 정리의 결과다.
(밑바닥 메커니즘의 이름은 vectorcall 프로토콜 — 26장에서 다룬다.)

dis에서 `NULL + len`은 "NULL을 함께 깔았다"(일반 호출),
`NULL|self + bark`는 "메서드 변형이다"(self를 남겼다)는 표기다.

## 개념 5 — u2 유제 3을 다시 읽기

deco_style의 바이트코드를 스택으로 트레이스하면:

```
LOAD_GLOBAL logger        [logger]            ← NULL 없음! (arg 0)
LOAD_CONST <code f>       [logger, 악보f]
MAKE_FUNCTION             [logger, 함수f]      ← 악보를 함수 객체로
CALL 0                    [wrapper]           ← 아래=logger가 함수, 위=f가 첫 인자
STORE_FAST f              []                  ← wrapper를 f에 저장
```

데코레이터는 **메서드 호출과 같은 모양**이다. 문법은 전혀 안 닮았지만
"함수 하나 + 인자 하나"라 컴파일러가 같은 형태를 재사용한다.
그래서 `CALL 0`인데도 인자 하나(f)가 넘어간다.

u2에서 본 manual_style과 비교하면 차이가 선명하다.
manual_style의 `logger(f)`는 일반 호출이라 `LOAD_GLOBAL 1 (NULL + logger)`로
NULL이 깔린다. 데코레이터는 `LOAD_GLOBAL 0 (logger)` — NULL이 없다.
같은 `logger(f)`인데 컴파일 결과가 다른 것이다.

## 자바와 비교 — 이번엔 "거의 같다"

JVM도 스택 머신이다. 자바의 콜 스택, 스택 트레이스, StackOverflowError가
전부 같은 구조에서 나온다. 파이썬 트레이스백 = 자바 스택 트레이스,
파이썬 RecursionError = 자바 StackOverflowError (파이썬은 프레임 개수 제한
방식: 기본 1000, `sys.getrecursionlimit()`).

차이 하나: 파이썬 프레임은 **일급 객체**다. `sys._getframe()`으로 실행 중인
프레임을 코드에서 직접 꺼내 만질 수 있다. 이 개방성이 디버거(pdb), pytest의
에러 리포트, 제너레이터(프레임을 살려두고 나가기)의 기반이다.

## 관측 — pvmlab

`tools/pvmlab/`은 이 유닛부터 커리큘럼의 **공식 관측 장비**다.
진짜 바이트코드를 `dis`로 읽고 평가 루프만 재현해서, 매 명령마다
프레임 스택·값 스택·지역 변수를 HTML로 기록한다. 모든 데모는 진짜 CPython과
assert 대조를 통과한다 — 관측 결과를 믿어도 된다는 뜻이다.

```bash
cd tools/pvmlab
python run.py ch00        # 00장 데모 → pvm_trace.html, 브라우저에서 ←/→
```

**사용 규칙**
- HTML 트레이스는 언제 어느 장 것을 봐도 좋다 (전체 지도를 훑는 행위)
- 엔진 코드(`engine/`)를 뜯는 것은 해당 장에 도착했을 때 (디테일 작업)
- 커리큘럼이 각 장을 통과할 때마다 그 부분의 엔진 코드가 "설명 가능"해지는 것이
  목표다. 33장이 끝나면 pvmlab 전체가 설명 가능한 코드가 된다.

## 백엔드 관점

- 에러 로그의 트레이스백을 "프레임 체인 덤프"로 읽게 되면, 내 코드 프레임과
  프레임워크 프레임을 구분하며 읽는 속도가 달라진다.
- Sentry가 각 프레임의 지역 변수 값을 보여줄 수 있는 이유 = 프레임 일급 객체.
- 제너레이터/코루틴의 "실행을 멈췄다 재개한다"의 실체가 "프레임을 콜 스택에서
  떼어 보관한다"이다 (pvmlab의 '보관된 프레임' 패널이 이걸 그대로 보여준다
  — 10장에서 정식으로 다룬다). asyncio의 뿌리가 여기 있다.
