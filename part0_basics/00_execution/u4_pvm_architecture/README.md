# u4. PVM은 스택 머신이다 — 바이트코드가 읽히기 시작하는 지점

## 질문

`LOAD_CONST`, `CALL`, `STORE_FAST` 같은 명령들은 대체 "어디에" 값을 올리고
"어디서" 꺼내는 것인가? PVM은 내부적으로 어떻게 생겼는가?

## 개념 1 — 값 스택

PVM은 **스택 머신**이다. 모든 계산이 **값 스택(value stack)** 하나를 중심으로 돈다.

- `LOAD_*` = 값을 스택 **위에 올린다** (push)
- 연산/호출 = 스택 위에서 필요한 만큼 **꺼내서**(pop) 계산하고, 결과를 **다시 올린다**
- `STORE_*` = 스택 맨 위 값을 꺼내 이름에 저장한다

`x = a + b`를 손으로 트레이스하면:

```
바이트코드           스택 상태 (오른쪽이 위)
─────────────────────────────────────
LOAD_FAST a          [a값]
LOAD_FAST b          [a값, b값]
BINARY_OP +          [a+b]          ← 두 개 꺼내 더하고 결과를 올림
STORE_FAST x         []             ← 맨 위를 꺼내 x에 저장
```

함수 호출 `f(10)`은:

```
LOAD_GLOBAL f        [f]
LOAD_CONST 10        [f, 10]
CALL 1               [반환값]       ← 인자 1개와 함수를 꺼내 호출, 결과를 올림
```

CALL 뒤의 숫자가 "스택에서 꺼낼 인자 개수"다. 이제 dis 출력의 숫자들이 의미를 갖는다.

## 개념 2 — u2 유제 3을 다시 읽기

deco_style의 바이트코드를 스택으로 트레이스하면:

```
LOAD_GLOBAL logger        [logger]
LOAD_CONST <code f>       [logger, 악보f]
MAKE_FUNCTION             [logger, 함수f]     ← 악보를 꺼내 함수 객체로 바꿔 올림
CALL 0*                   [wrapper]           ← logger(f) 실행, 반환값이 올라옴
STORE_FAST f              []                  ← wrapper를 f라는 이름에 저장
```

이제 보인다: **logger를 "먼저" 스택에 올려두고**, 그 위에 f를 만든 다음,
CALL이 둘을 한꺼번에 소비한다. "장식 전의 f가 이름에 묶이는 순간이 없다"는 게
스택 그림에서는 자명하다 — f는 스택 위에서 태어나 스택 위에서 바로 logger에게 먹힌다.

(* CALL 0인 이유: 3.11+에서 데코레이터 호출은 인자 배치 방식이 약간 달라
표기가 0으로 나온다. 지금은 "logger가 f를 받아 호출된다"로 읽으면 충분하다.)

## 개념 3 — 프레임: 함수 호출마다 생기는 작업 공간

값 스택은 하나가 아니다. **함수 호출마다 프레임(frame)이 새로 만들어지고,
프레임마다 자기만의 값 스택과 지역 변수 공간을 갖는다.**

프레임에 들어 있는 것:
- 실행 중인 코드 객체 참조 (어느 악보를 연주 중인가)
- 지역 변수 배열 (`LOAD_FAST`가 인덱스로 바로 접근하는 곳)
- 값 스택
- 현재 실행 위치 (몇 번째 명령까지 했나)
- **호출자의 프레임 링크** (누가 나를 불렀나)

`main() → f() → g()`처럼 호출이 겹치면 프레임이 사슬로 쌓인다.
이 사슬이 **콜 스택**이고, 예외가 났을 때 보는 **트레이스백이 바로 이 사슬을
출력한 것**이다. `Traceback (most recent call last)` — 프레임 체인을
바깥에서 안쪽으로 읽어준 것일 뿐이다.

정리하면 이름이 세 가지 나왔는데 혼동 주의:
- **값 스택**: 프레임 안에서 계산에 쓰는 작은 스택
- **콜 스택**: 프레임들이 쌓인 사슬
- 코드 객체 / 함수 객체 / **프레임**: 악보 / 연주자 / **연주 1회의 무대**.
  u2에서 "호출될 때마다 새로 생기는 건 뭔가?"의 답이 이것이다.

## 자바와 비교 — 이번엔 "거의 같다"

JVM도 스택 머신이다. 자바의 콜 스택, StackOverflowError, 스택 트레이스가
전부 같은 구조에서 나온다. 파이썬 트레이스백 = 자바 스택 트레이스.
파이썬 `RecursionError` = 자바 `StackOverflowError` (파이썬은 프레임 개수
제한 방식이라는 차이만 있다. 기본 1000개, `sys.getrecursionlimit()`).

차이 하나: 파이썬 프레임은 **일급 객체**다. `sys._getframe()`으로 실행 중인
프레임을 코드에서 직접 꺼내 만질 수 있다. 자바에서 스택 프레임을 객체로
꺼내는 건 훨씬 제한적이다. 이 개방성이 디버거(pdb), pytest의 마법 같은
에러 리포트, 제너레이터(프레임을 살려두고 나가기)의 기반이 된다.

## 백엔드 관점

- 에러 로그의 트레이스백을 "프레임 체인 덤프"로 읽게 되면, 어느 프레임이
  내 코드고 어느 프레임이 프레임워크인지 구분하며 읽는 속도가 달라진다.
- Sentry 같은 에러 트래커가 "각 프레임의 지역 변수 값"을 보여줄 수 있는
  이유 = 프레임이 일급 객체라서.
- 제너레이터/코루틴(10장, 24장)의 "실행을 멈췄다 재개한다"의 실체가
  "프레임을 콜 스택에서 떼어내 보관한다"이다. asyncio의 뿌리가 여기 있다.

## 실무 규칙 (EP 연결)

- 재귀 깊이 제한(RecursionError)은 프레임이 실제 메모리를 먹는 구조에서
  나온 안전장치다. 깊은 재귀는 반복문으로 바꾸는 게 파이썬의 관례다.
- Item 87 (traceback 모듈로 향상된 예외 리포팅)이 가능한 이유가 프레임
  일급 객체다 — 19장에서 원리와 함께 회수한다.
