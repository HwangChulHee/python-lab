# u2. 슬라이싱 — 인덱스가 아니라 경계다

## 지도 확인

u1에서 `for`가 이터레이터 프로토콜로 동작한다는 걸 봤다.
이번엔 시퀀스의 다른 축 — **인덱싱과 슬라이싱**이다.
`__getitem__`이라는 또 하나의 프로토콜이고, off-by-one 버그의 온상이며,
슬라이스가 새 객체를 만드는지 아닌지가 01장(가변성)과 연결된다.

## 개념 1 — 슬라이스는 [시작, 끝) 반열림 구간

```python
s = [0, 1, 2, 3, 4]
s[1:3]        # [1, 2]  — 3은 포함 안 됨
```

**끝 인덱스는 제외된다.** 이건 실수가 아니라 의도된 설계다.
인덱스를 "칸 번호"가 아니라 **"칸 사이의 경계"**로 보면 자연스럽다.

```
 요소:    0    1    2    3    4
경계:   0    1    2    3    4    5
        ↑         ↑
      s[0:2] = [0, 1]
```

이 설계의 이득:

```python
len(s[a:b]) == b - a          # 길이 계산이 뺄셈 하나
s[:k] + s[k:] == s            # 어느 지점에서 잘라도 합치면 원본
```

파이썬 창시자 귀도가 직접 설명한 근거다. 자바 `substring(a, b)`,
C++ 이터레이터 범위도 같은 규칙을 쓴다.

## 개념 2 — 세 번째 인자: step

```python
s = [0, 1, 2, 3, 4, 5]
s[::2]        # [0, 2, 4]      두 칸씩
s[1::2]       # [1, 3, 5]      1부터 두 칸씩
s[::-1]       # [5,4,3,2,1,0]  뒤집기
s[::-2]       # [5, 3, 1]      뒤에서 두 칸씩
```

`s[::-1]`이 뒤집기 관용구지만, **stride와 slice를 한 번에 쓰면 읽기 어렵다.**

```python
s[2:7:2]      # 무슨 뜻인지 즉시 안 읽힌다
```

EP의 권고: **stride와 start/end를 같이 쓰지 말 것.** 나눠 쓴다.

```python
part = s[2:7]
result = part[::2]
```

## 개념 3 — 범위를 넘어가도 에러가 안 난다

인덱싱과 슬라이싱의 결정적 차이다.

```python
s = [1, 2, 3]
s[10]         # IndexError!
s[10:20]      # []  — 에러 없음
s[1:100]      # [2, 3]  — 알아서 잘림
```

슬라이싱은 **범위를 알아서 클램핑**한다. 편리하지만,
"왜 빈 리스트가 나오지?"를 조용히 만드는 원인이기도 하다.

## 개념 4 — 슬라이스는 얕은 복사를 만든다

```python
a = [1, 2, 3]
b = a[:]           # 전체 슬라이스 = 얕은 복사
b is a             # False — 새 객체!
b.append(4)
a                  # [1, 2, 3] — 영향 없음
```

01장 u4에서 본 `list(a)`와 같은 수준의 복사다. **바깥 리스트만 새로,
안쪽 원소는 공유**한다.

```python
a = [[1, 2], [3, 4]]
b = a[:]
b[0].append(99)
a                  # [[1,2,99],[3,4]] — 안쪽은 공유!
```

## 개념 5 — 슬라이스에 대입하면 길이가 바뀐다

```python
a = [1, 2, 3, 4, 5]
a[1:3] = ["x"]     # 2개를 1개로 교체
a                  # [1, 'x', 4, 5]  — 길이가 줄었다!

a = [1, 2, 3]
a[1:2] = ["a", "b", "c"]
a                  # [1, 'a', 'b', 'c', 3]  — 길이가 늘었다
```

**슬라이스 대입은 in-place 변경(mutation)이다.** 01장 기준으로
`a[1:3] = ...`는 재대입이 아니라 변경이므로, 다른 이름으로 공유 중이면
그쪽에도 반영된다.

```python
a = [1, 2, 3]
b = a
a[:] = [9, 9, 9]   # 변경 — b도 바뀜
b                  # [9, 9, 9]

a = [1, 2, 3]
b = a
a = [9, 9, 9]      # 재대입 — b는 그대로
b                  # [1, 2, 3]
```

`a[:] = ...`는 "내용물 전체 교체"라는 관용구로 쓰인다.

## 개념 6 — 슬라이스 객체와 __getitem__

`s[1:3]`은 문법 설탕이다. 실제로는:

```python
s[1:3]  →  s.__getitem__(slice(1, 3, None))
s[2]    →  s.__getitem__(2)
```

`slice`는 진짜 객체다.

```python
sl = slice(1, 3)
s[sl]              # s[1:3]과 같음
sl.start, sl.stop, sl.step
```

그래서 **`__getitem__`만 구현하면 내 클래스도 인덱싱/슬라이싱이 된다.**
u1의 이터레이터 프로토콜과 같은 방식 — 타입이 아니라 메서드가 있는지를 본다.

덤: `__getitem__`만 있고 `__iter__`가 없어도 `for`가 동작한다.
파이썬이 0, 1, 2...로 인덱싱을 시도하다 `IndexError`가 나면 멈추는
**구형 이터레이션 프로토콜**이 남아 있기 때문이다.

## 자바와 비교

| | 자바 | 파이썬 |
|---|---|---|
| 부분 추출 | `list.subList(a, b)`, `s.substring(a,b)` | `s[a:b]` |
| 끝 제외 | 동일 (반열림) | 동일 |
| 음수 인덱스 | 없음 | `s[-1]` = 마지막 |
| 범위 초과 | 예외 | 슬라이싱은 조용히 클램핑 |
| 역순 | `Collections.reverse` | `s[::-1]` |

`subList`는 **뷰(view)**라 원본과 연결되지만, 파이썬 슬라이스는
**새 리스트를 복사**한다. 이 차이는 성능에도 영향이 있다 —
큰 리스트를 자주 슬라이싱하면 복사 비용이 든다.
(복사 없이 보려면 27장의 `memoryview`를 쓴다)

## 백엔드 관점

- 페이지네이션에서 `items[offset:offset+limit]`은 **범위 초과가 안전**하다.
  마지막 페이지에서 자동으로 잘린다.
- 대용량 리스트 슬라이싱은 복사 비용이 있다. DB LIMIT/OFFSET으로
  넘기는 게 정석인 이유 중 하나.
- `data[:]`로 방어적 복사를 자주 쓴다. 단, 얕은 복사임을 기억할 것.

## 실무 규칙 (EP 연결)

- **stride와 start/end를 한 슬라이스에 같이 쓰지 않는다** (EP Item 19).
  나눠 쓰거나 `itertools.islice`를 쓴다.
- `s[0:len(s)]` 대신 `s[:]`. 시작이 0이거나 끝이 마지막이면 생략한다 (EP Item 18).
- 슬라이스 대입은 mutation임을 의식한다. 공유 중인 리스트에 주의.

## 3문장 요약 (직접 작성)

1. 슬라이스는 [시작, 끝)의 문법으로 리스트를 자른다.
2. 슬라이스 할당은 얕은 복사를 만들고, 슬라이스 문법을 포함한 대입은 객체를 바꾸는 mutation이다.
3. 클래스내 getitem를 통해 클래스의 슬라이싱을 적용시킬수 있다.
