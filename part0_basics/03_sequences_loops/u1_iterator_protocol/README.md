# u1. for문은 반복문이 아니다 — 이터레이터 프로토콜

## 지도 확인

02장에서 `if x:`가 `__bool__`/`__len__`을 호출한다는 걸 봤다.
파이썬이 타입을 검사하는 게 아니라 **객체에게 메서드를 묻는** 방식이었다.

`for`도 정확히 같다. `for`는 카운터를 돌리는 문법이 아니라
**객체에게 "순회할 방법을 달라"고 요청하는** 문법이다.
이 유닛이 03장 전체의 토대이고, 10장(제너레이터)과 24장(asyncio)까지 이어진다.

## 개념 1 — 자바/C의 for와 다르다

C나 자바의 전통적 `for`는 **카운터를 증가시키는 반복문**이다.

```java
for (int i = 0; i < n; i++) { ... }   // 초기화·조건·증감이 문법에 박혀 있음
```

파이썬 `for`에는 그런 게 없다.

```python
for x in items:
    ...
```

초기화도, 조건도, 증감도 없다. `items`에게 **"다음 값 줘"**를 반복해서
물어볼 뿐이다. 그래서 `range(n)`도 "n까지 세는 것"이 아니라
**그냥 순회 가능한 객체**일 뿐이다.

## 개념 2 — for가 실제로 하는 일

```python
for x in items:
    body(x)
```

이 코드는 개념적으로 다음과 완전히 같다.

```python
it = iter(items)          # ① 이터레이터를 얻는다
while True:
    try:
        x = next(it)      # ② 다음 값을 요청한다
    except StopIteration: # ③ 더 없으면 이 예외가 온다
        break
    body(x)
```

**세 가지가 전부다.**

1. `iter(obj)` → `obj.__iter__()`를 호출해 **이터레이터**를 받는다
2. `next(it)` → `it.__next__()`를 호출해 값을 하나 받는다
3. 값이 떨어지면 `__next__`가 `StopIteration` 예외를 던지고, `for`가 잡아서 멈춘다

`for`는 문법 설탕이다. 실제 동작은 메서드 호출 두 개와 예외 하나다.

## 개념 3 — 이터러블 vs 이터레이터 (제일 중요)

둘은 **다른 것**이다. 이걸 구분 못 하면 이후가 전부 헷갈린다.

| | 이터러블 (iterable) | 이터레이터 (iterator) |
|---|---|---|
| 가진 메서드 | `__iter__` | `__iter__` **와** `__next__` |
| 역할 | "순회할 수 있다" | "지금 어디까지 갔는지 기억한다" |
| 예 | list, tuple, str, dict, range | `iter(lst)`의 결과, 제너레이터, 파일 객체 |
| 재사용 | 여러 번 순회 가능 | **한 번 쓰면 끝** |

```python
lst = [1, 2, 3]        # 이터러블
it = iter(lst)         # 이터레이터 (lst와 다른 객체!)

next(it)               # 1
next(it)               # 2
next(it)               # 3
next(it)               # StopIteration!
```

**리스트는 소진되지 않는다. 이터레이터가 소진된다.**
`for x in lst`를 두 번 돌리면 매번 `iter(lst)`로 **새 이터레이터**를 만들기
때문에 두 번 다 잘 돈다. 하지만 이터레이터를 직접 두 번 돌리면 두 번째는 빈다.

```python
it = iter([1, 2, 3])
list(it)               # [1, 2, 3]
list(it)               # []  ← 이미 소진됨!
```

**이터레이터도 `__iter__`를 갖는다.** 자기 자신을 반환한다.
그래야 `for x in it:`이 동작하기 때문이다.

## 개념 4 — 소진 함정

파일 객체와 제너레이터가 이터레이터라서 실무에서 자주 걸린다.

```python
with open("data.txt") as f:
    lines = f.readlines()      # 여기서 이미 소진
    for line in f:             # 아무것도 안 돎!
        ...
```

```python
data = (x*2 for x in range(3))   # 제너레이터 = 이터레이터
print(list(data))                # [0, 2, 4]
print(list(data))                # []  ← 두 번째는 빈다
print(sum(data))                 # 0
```

**증상**: "분명 데이터가 있었는데 두 번째 순회에서 사라진다."
**원인**: 이터레이터를 이터러블처럼 재사용하려 했다.
**해결**: 여러 번 써야 하면 `list()`로 실체화하거나, 매번 새로 만든다.

## 개념 5 — range는 리스트가 아니다

```python
range(1_000_000)                  # 즉시 반환. 메모리 거의 안 씀
sys.getsizeof(range(1_000_000))   # 48바이트
sys.getsizeof(list(range(1_000_000)))  # 8MB 이상
```

`range`는 **값을 저장하지 않는다.** start/stop/step 세 개만 들고 있다가,
`__iter__`가 호출되면 그때그때 계산해서 내놓는다.

그런데 `range`는 이터레이터가 **아니다.** 이터러블이다.

```python
r = range(3)
list(r)      # [0, 1, 2]
list(r)      # [0, 1, 2]  ← 다시 돌아도 나온다 (매번 새 이터레이터)
```

`len(range(...))`도 되고 `r[5]` 인덱싱도 된다. 이터레이터로는 못 하는 일이다.

## 개념 6 — 바이트코드

```python
for x in items:
    pass
```

```
LOAD_FAST items
GET_ITER              ← iter(items) 호출. 이터레이터를 스택에 올림
FOR_ITER  →끝         ← next() 호출. StopIteration이면 점프로 탈출
STORE_FAST x          ← 받은 값을 x에
  (본문)
JUMP_BACKWARD         ← FOR_ITER로 돌아감
END_FOR               ← 소진된 이터레이터를 스택에서 정리
```

주목할 점: **`StopIteration`이 예외인데 try/except가 안 보인다.**
`FOR_ITER`가 내부적으로 처리해서 점프로 바꾼다.
그래서 매 반복마다 예외 객체를 만드는 비용은 들지 않는다.

## 자바와 비교 — "거의 같다"

자바의 향상된 for문이 정확히 같은 구조다.

```java
for (String s : list) { ... }
// 컴파일러가 이렇게 바꿈:
Iterator<String> it = list.iterator();
while (it.hasNext()) { String s = it.next(); ... }
```

| | 자바 | 파이썬 |
|---|---|---|
| 이터러블 | `Iterable` 인터페이스 (`iterator()`) | `__iter__` 있는 객체 |
| 이터레이터 | `Iterator` (`hasNext()`, `next()`) | `__next__` 있는 객체 |
| 종료 신호 | `hasNext()`가 false | `StopIteration` 예외 |
| 소진 | 한 번 쓰면 끝 (동일) | 한 번 쓰면 끝 (동일) |

**차이는 종료 방식 하나다.** 자바는 "다음 있냐?"를 미리 묻고(look-ahead),
파이썬은 "일단 달라"고 한 뒤 없으면 예외를 받는다.

파이썬 방식의 장점: `hasNext`를 구현하려면 다음 값을 미리 읽어둬야 하는데
(파일이나 네트워크에서 그게 어렵다), 예외 방식은 그럴 필요가 없다.
단점: 예외를 제어 흐름에 쓰는 게 어색해 보인다 — 하지만 파이썬은
EAFP(일단 해보고 예외 처리) 문화라 자연스럽다 (19장에서 다룬다).

## 백엔드 관점

- **파일·DB 커서·HTTP 스트림이 전부 이터레이터다.** 한 번만 순회 가능하다는
  성질이 그대로 적용된다. "왜 두 번째 루프가 안 돌지?"의 90%가 이 문제다.
- 대용량 처리에서 리스트 대신 이터레이터를 쓰면 메모리가 상수로 유지된다.
  100만 행 CSV를 `readlines()`로 읽으면 다 올라가지만, `for line in f`는
  한 줄씩만 메모리에 둔다.
- FastAPI의 `StreamingResponse`, SQLAlchemy의 `yield_per`가 전부 이 원리다.
- `__iter__`만 구현하면 내가 만든 클래스도 `for`에 넣을 수 있다.
  타입이 아니라 프로토콜로 동작하기 때문이다 (09장에서 정식화).

## 실무 규칙 (EP 연결)

- 이터레이터를 함수 인자로 받으면 **한 번만 순회 가능**하다는 걸 문서화하거나,
  방어적으로 `list()`로 실체화한다 (EP Item 21 계열).
- 여러 번 순회해야 하면 이터레이터가 아니라 **이터러블을 받는다.**
  (컨테이너를 받거나, 매번 새 이터레이터를 만드는 팩토리를 받는다)
- `range(len(x))`로 인덱스를 돌리지 않는다 — `enumerate`를 쓴다 (u4에서, EP Item 17).

## 3문장 요약 (직접 작성)

1. for문은 이터러블을 받아서 순회하는 기능을 가진 문법이다.
2. 이터러블은 __iter__를 가진, 순회가능한 객체이고 이터레이터는 순회에 대한 정보를 담는 객체이다.
3. 그래서 이터러블은 여러번 사용이 가능하고, 이터레이터는 한번 사용하면 소진된다.
