# u1. GIL — 무엇을 보호하고 무엇을 보호하지 않는가

## 지도 확인

지금까지는 "코드 한 줄이 어떻게 실행되는가"였다.
이제 **여러 실행 흐름이 동시에 있을 때** 무슨 일이 생기는지로 넘어간다.

그리고 그 출발점이 01장 u1에서 본 `ob_refcnt`다.
GIL은 추상적인 동시성 이론이 아니라, **참조 카운팅을 지키기 위한
지극히 구현적인 장치**다. 이 인과를 이해하는 것이 이 유닛의 전부다.

## 개념 1 — GIL이란 무엇인가

**Global Interpreter Lock**: CPython 인터프리터 전체에 걸린 **락 하나**.

> 한 프로세스 안에서, **한 순간에 오직 하나의 스레드만** 파이썬
> 바이트코드를 실행할 수 있다.

스레드를 10개 만들어도 파이썬 코드는 항상 1개만 돈다. 나머지 9개는
GIL을 기다린다. 멀티코어 CPU여도 마찬가지다 — 코어가 8개든 GIL은 하나다.

**중요한 단서**: 이건 **CPython의 구현 선택**이지 파이썬 언어 명세가 아니다.
Jython, IronPython에는 GIL이 없다. "파이썬은 GIL 때문에 느리다"는 부정확하고,
"CPython은 GIL 때문에"가 정확하다 (00장 u1의 CPython vs 파이썬 구분).

## 개념 2 — 왜 존재하는가: refcount가 원인이다

01장 u1의 구조를 다시 보자.

```c
typedef struct _object {
    Py_ssize_t ob_refcnt;      // ← 이것
    PyTypeObject *ob_type;
} PyObject;
```

`b = a`를 하면 `ob_refcnt`가 1 증가한다. 그런데 이 증가는 기계어 수준에서
**세 단계**다.

```
1. 메모리에서 현재 값을 읽는다        (예: 5)
2. 1을 더한다                        (6)
3. 메모리에 다시 쓴다                 (6)
```

두 스레드가 동시에 이걸 하면:

```
스레드 A: 읽음(5)  ...            더함(6)  씀(6)
스레드 B:          읽음(5) 더함(6)              씀(6)
결과: refcount = 6   ← 두 번 증가했는데 6! (7이어야 함)
```

**refcount가 실제보다 작아진다.** 그러면 아직 쓰고 있는 객체가 0에 도달해
**해제되고, 다음 접근에서 프로세스가 죽는다.** 반대 방향이면 영원히 해제되지
않아 메모리 누수다.

객체가 수백만 개인데 각각에 락을 걸면 락 비용이 프로그램을 지배한다.
그래서 CPython은 **인터프리터 전체에 락 하나**를 걸어 이 문제를 통째로 해결했다.
간단하고, 싱글스레드 성능이 좋고, C 확장 작성이 쉬워진다.

**GIL은 게으름이 아니라 트레이드오프다.**

## 개념 3 — 언제 GIL을 놓는가

GIL을 영원히 붙들고 있으면 다른 스레드는 굶어 죽는다. 두 경우에 놓는다.

**(1) IO 대기에 들어갈 때 — 이게 핵심이다**

```python
data = sock.recv(1024)     # 네트워크 대기 → GIL 해제
line = f.readline()        # 디스크 대기 → GIL 해제
time.sleep(1)              # 명시적 대기 → GIL 해제
cursor.execute(sql)        # DB 응답 대기 → GIL 해제
```

IO는 CPU가 할 일이 없는 시간이다. 그동안 GIL을 붙들 이유가 없으니
놓아주고, 다른 스레드가 파이썬 코드를 돌린다.

**그래서 IO-bound 작업은 멀티스레드가 효과적이다.**

**(2) 일정 시간이 지나면 (선점)**

CPU 작업만 하는 스레드가 GIL을 독점하지 않도록, 기본 5ms마다
"다른 스레드에게 넘겨라"는 요청이 걸린다.

```python
import sys
sys.getswitchinterval()    # 0.005 (초)
```

3.2 이전에는 "100개 바이트코드마다" 방식이었고, 이게 여러 문제를 일으켜
시간 기반으로 바뀌었다.

**(3) C 확장이 명시적으로 놓을 때**

numpy, pandas 같은 라이브러리는 무거운 계산을 C에서 할 때
`Py_BEGIN_ALLOW_THREADS`로 GIL을 놓는다. 파이썬 객체를 안 건드리는
구간이라 안전하다. **그래서 numpy 연산은 멀티스레드로 병렬화가 된다.**

## 개념 4 — GIL은 스레드 안전을 보장하지 않는다 (제일 중요)

가장 흔한 오해다. "한 번에 하나만 도니까 안전하겠지"는 **틀렸다.**

```python
count = 0

def increment():
    global count
    for _ in range(100_000):
        count += 1

# 스레드 2개로 실행하면 200_000이 나오지 않는다
```

이유: `count += 1`이 **바이트코드 여러 개**다.

```
LOAD_GLOBAL count      ← 읽고
LOAD_CONST 1
BINARY_OP +            ← 더하고
STORE_GLOBAL count     ← 쓴다
```

GIL은 **바이트코드 하나의 실행 중에는** 스레드 전환을 막지만,
**명령과 명령 사이**에서는 전환이 일어날 수 있다.

```
스레드 A: LOAD(5) ...              BINARY(6) STORE(6)
스레드 B:         LOAD(5) BINARY(6)                   STORE(6)
결과: 6  ← 두 번 증가했는데 6
```

**refcount에서 봤던 그 문제가 파이썬 레벨에서 그대로 재현된다.**
GIL은 인터프리터 내부 자료구조를 지킬 뿐, **내 코드의 논리적 원자성은
지켜주지 않는다.**

07장 u1 유제 4에서 "전역 카운터가 위험하다"고 했던 게 이 이야기다.

**해결**: 직접 락을 건다.

```python
from threading import Lock
lock = Lock()

def increment():
    global count
    for _ in range(100_000):
        with lock:            # 임계 구역
            count += 1
```

## 개념 5 — 무엇이 원자적인가

일부 연산은 단일 바이트코드라 원자적이다.

```python
lst.append(x)        # 원자적 (C 레벨에서 한 번에)
d[k] = v             # 원자적
x = y                # 원자적 (단순 대입)

count += 1           # 원자적 아님 (읽기-수정-쓰기)
lst[0] += 1          # 원자적 아님
if k not in d: d[k]=v  # 원자적 아님 (검사와 대입 사이에 전환 가능)
```

하지만 **이걸 외워서 의존하지 마라.** 버전에 따라 바뀔 수 있고,
읽는 사람이 의도를 알 수 없다. 공유 상태를 수정한다면 **락을 쓴다.**

## 개념 6 — 그래서 무엇이 병렬화되나

| 작업 | 멀티스레드 효과 | 이유 |
|---|---|---|
| 네트워크 요청 (HTTP, DB) | **좋음** | 대기 중 GIL 해제 |
| 파일 읽기/쓰기 | **좋음** | 동일 |
| numpy/pandas 대량 연산 | **좋음** | C에서 GIL 해제 |
| 순수 파이썬 계산 | **없음 (오히려 느려짐)** | GIL 경쟁 + 전환 비용 |
| 이미지 처리 (순수 파이썬) | 없음 | 동일 |

**CPU-bound는 멀티프로세싱으로 간다.** 프로세스마다 인터프리터가
따로 있으니 GIL도 따로다. 대신 프로세스 간 데이터 전달에 직렬화 비용이 든다.

u2에서 이걸 실측한다.

## 개념 7 — free-threading (3.13+)

PEP 703으로 **GIL 없는 CPython**이 실험적으로 도입됐다 (3.13, 빌드 옵션).

- GIL을 제거하고 객체마다 세밀한 락 + biased reference counting 사용
- CPU-bound 멀티스레드가 실제로 병렬 실행됨
- 대가: 싱글스레드 성능 하락(초기 ~40%, 개선 중), C 확장 호환성 문제

당장 실무에 쓸 단계는 아니지만, **GIL이 언어의 본질이 아니라
구현 선택이었다는 증거**로서 의미가 있다.

면접에서 "GIL이 파이썬의 한계인가요?"에 답할 때:
"CPython 구현의 트레이드오프이고, 3.13부터 free-threading 빌드가
실험적으로 제공됩니다"가 정확한 답이다.

## 자바와 비교 — "락의 단위가 다르다"

자바는 **진짜 멀티스레드 병렬 실행**이 된다. GIL 같은 전역 락이 없다.

```java
// 자바: 8코어면 8개 스레드가 진짜 동시에 CPU를 씀
```

대신 자바는 **개발자가 직접 동기화**를 책임진다. `synchronized`,
`volatile`, `AtomicInteger`, `ConcurrentHashMap` 같은 도구가
언어와 표준 라이브러리에 두텁게 갖춰진 이유다.

| | 자바 | CPython |
|---|---|---|
| 병렬 실행 | 진짜 병렬 | GIL로 직렬화 |
| 락 단위 | 객체별 (개발자가 선택) | 인터프리터 전체 (자동) |
| 메모리 관리 | GC (스레드 안전) | refcount (GIL로 보호) |
| CPU-bound 병렬 | 스레드로 해결 | 프로세스로 해결 |
| race condition | 개발자 책임 | **개발자 책임 (동일!)** |

**결정적 공통점**: 둘 다 `count++` / `count += 1`은 원자적이지 않다.
자바의 `AtomicInteger`가 존재하는 이유와 파이썬에 `Lock`이 필요한 이유가 같다.

**차이는 "무엇을 자동으로 지켜주는가"다.** GIL은 인터프리터 내부를
지켜주지만 내 코드는 안 지켜준다. 자바는 아무것도 자동으로 안 지켜준다.

## 백엔드 관점

- **웹 서버 대부분은 IO-bound다.** DB 조회, 외부 API, 파일 IO가 응답 시간의
  대부분이고 그동안 GIL은 해제된다. **그래서 GIL이 있어도 파이썬 웹 서버가
  잘 돈다.** 00장 u1에서 "IO-bound에서는 언어 속도가 병목이 아니다"라고 한
  것과 같은 맥락이다.
- 문제는 **CPU 작업이 요청 처리에 끼어들 때**다. 이미지 리사이징, 큰 JSON
  파싱, 암호화 연산이 들어가면 그 시간 동안 다른 요청이 전부 막힌다.
  → 별도 워커 프로세스나 작업 큐(Celery)로 빼는 이유.
- **gunicorn 워커 수**: `workers = 2 * CPU코어 + 1`이 관례인데, 이건
  "프로세스마다 GIL이 따로"라서 코어를 다 쓰려고 프로세스를 여러 개
  띄우는 것이다. u2에서 자세히.
- 전역 상태(캐시, 카운터)를 여러 스레드가 수정한다면 **GIL과 무관하게
  락이 필요하다.**

## 실무 규칙

- 공유 가변 상태를 수정할 땐 락을 건다. "GIL이 있으니까 괜찮겠지"는 틀렸다.
- 가능하면 공유 상태 자체를 없앤다 (큐로 넘기기, 불변 객체 쓰기).
- CPU-bound는 프로세스로, IO-bound는 스레드나 asyncio로.
- "파이썬은 GIL 때문에" → "CPython은 GIL 때문에"로 말한다.
