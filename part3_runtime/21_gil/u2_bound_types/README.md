# u2. IO-bound vs CPU-bound — 무엇을 언제 쓰나

## 지도 확인

u1에서 GIL이 무엇이고 왜 존재하는지 봤다.
이번엔 **그래서 실무에서 뭘 선택할 것인가**다.
스레드/프로세스/asyncio를 언제 쓰는지, 그 근거를 숫자로 확인한다.

## 개념 1 — 두 가지 bound

**IO-bound**: 대부분의 시간을 **기다리는 데** 쓴다. CPU는 논다.
- 네트워크 요청 (HTTP, DB 조회, 외부 API)
- 파일 읽기/쓰기
- 사용자 입력 대기

**CPU-bound**: 대부분의 시간을 **계산하는 데** 쓴다. CPU가 100%다.
- 대량 수치 연산, 정렬, 암호화
- 이미지/영상 처리
- 압축, 파싱

구분법: **작업 중 CPU 사용률을 보면 된다.** 100%에 가까우면 CPU-bound,
낮으면 IO-bound다.

## 개념 2 — GIL이 만드는 결론

u1에서 봤듯 GIL은 **IO 대기 중에 해제**된다.

```
IO-bound + 스레드 4개
스레드1: [요청]------대기------[처리]     ← 대기 중 GIL 해제
스레드2:    [요청]------대기------[처리]
스레드3:       [요청]------대기------[처리]
스레드4:          [요청]------대기------[처리]
→ 4배 가까이 빨라진다
```

```
CPU-bound + 스레드 4개
스레드1: [계산][      대기       ][계산]   ← GIL 경쟁
스레드2: [대기][계산][    대기    ]
스레드3: ...
→ 빨라지지 않는다. 전환 비용 때문에 오히려 느려질 수도
```

**결론**:
- IO-bound → **스레드** 또는 **asyncio**
- CPU-bound → **프로세스** (멀티프로세싱)

## 개념 3 — 예외: C 확장은 GIL을 놓는다

CPU-bound인데도 스레드가 먹히는 경우가 있다.

```python
import numpy as np
big = np.random.rand(10_000_000)
result = big.sum()          # C에서 계산, GIL 해제 → 스레드 병렬 가능
```

numpy, pandas, hashlib, zlib, Pillow 등은 무거운 연산을 C에서 수행하며
`Py_BEGIN_ALLOW_THREADS`로 GIL을 놓는다. 파이썬 객체를 안 건드리는
구간이라 안전하다.

**판단 질문 두 단계**:
1. CPU-bound인가 IO-bound인가?
2. CPU-bound라면, 그 계산이 **C에서** 일어나는가?

둘 다 통과하면(CPU + C 구현) 스레드가 효과적이다.
순수 파이썬 계산이면 프로세스로 가야 한다.

## 개념 4 — 프로세스의 비용

멀티프로세싱이 만능은 아니다.

**비용 1: 메모리** — 프로세스마다 인터프리터가 통째로 뜬다. 수십 MB씩.

**비용 2: 직렬화** — 프로세스 간에 객체를 직접 못 넘긴다. pickle로
직렬화해서 전송하고 역직렬화한다.

```python
# 큰 데이터를 넘기면 직렬화 비용이 계산 시간을 넘을 수 있다
with ProcessPoolExecutor() as ex:
    results = ex.map(process, huge_list)   # huge_list가 통째로 pickle됨
```

**비용 3: 시작 시간** — 프로세스 생성이 스레드보다 훨씬 느리다.

그래서 **작업 단위가 충분히 커야** 프로세스가 이득이다.
작은 작업 수천 개면 오버헤드가 이득을 먹는다.

**비용 4: 공유 상태 불가** — 전역 변수를 공유하지 않는다.
`multiprocessing.Queue`, `Manager`, 공유 메모리를 써야 한다.

## 개념 5 — concurrent.futures로 통일

스레드와 프로세스를 **같은 인터페이스**로 쓸 수 있다.

```python
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

with ThreadPoolExecutor(max_workers=4) as ex:
    results = list(ex.map(io_task, items))

with ProcessPoolExecutor(max_workers=4) as ex:
    results = list(ex.map(cpu_task, items))
```

**둘을 바꿔가며 실측해보고 결정하는 게 정석이다.**
클래스 이름만 바꾸면 되므로 비교가 쉽다.

주의: `ProcessPoolExecutor`에 넘기는 함수는 **모듈 최상위에 정의**돼야 한다
(pickle 가능해야 하므로). lambda나 중첩 함수는 안 된다.

## 개념 6 — asyncio는 세 번째 선택지

IO-bound에는 스레드 말고 asyncio도 있다.

| | 스레드 | asyncio |
|---|---|---|
| 전환 | OS가 결정 (선점형) | 코드가 `await`에서 양보 (협조형) |
| 비용 | 스레드당 ~8MB 스택 | 코루틴당 수 KB |
| 동시성 규모 | 수백~수천 | **수만** |
| 코드 변경 | 기존 코드 그대로 | `async`/`await`로 전면 수정 |
| 라이브러리 | 기존 것 사용 가능 | 비동기 지원 라이브러리 필요 |

**동시 연결이 아주 많으면 asyncio, 적당하면 스레드**가 대략의 기준이다.
24~25장에서 정식으로 다룬다.

## 개념 7 — gunicorn 워커 수 (백엔드 실전)

`workers = 2 * CPU코어 + 1`이라는 관례가 있다. 근거를 뜯어보면:

**왜 프로세스인가**: 프로세스마다 인터프리터가 따로 있으니 **GIL도 따로**다.
코어 8개를 다 쓰려면 프로세스가 8개 이상 필요하다. 스레드로는 안 된다.

**왜 2배 + 1인가**: 웹 요청은 IO-bound라 워커가 대기하는 시간이 있다.
코어 수만큼만 띄우면 대기 중에 코어가 논다. 여유분을 둬서 활용률을 높인다.

**워커 클래스에 따라 다르다**:
- `sync` (기본): 워커당 요청 1개. 위 공식 적용
- `gthread`: 워커당 스레드 여러 개. IO-bound면 워커 수를 줄이고 스레드를 늘림
- `uvicorn`(ASGI): asyncio 기반. 워커 = 코어 수로 두고 동시성은 이벤트 루프가 처리

**메모리 제약**이 실질적 상한이다. 워커 하나가 200MB 먹는데 2GB 컨테이너면
공식과 무관하게 8개가 한계다.

## 자바와 비교

자바는 이 고민 자체가 다르다.

```java
ExecutorService pool = Executors.newFixedThreadPool(8);
// CPU-bound든 IO-bound든 스레드로 해결
```

자바는 GIL이 없어 **스레드가 진짜 병렬 실행**되므로, CPU-bound도
스레드 풀로 처리한다. 프로세스를 여러 개 띄울 이유가 없다.

| | 자바 | CPython |
|---|---|---|
| CPU-bound 병렬 | 스레드 풀 | **프로세스 풀** |
| IO-bound 병렬 | 스레드 풀 | 스레드 풀 또는 asyncio |
| 서버 배포 | JVM 1개 + 스레드 다수 | **프로세스 다수** (gunicorn) |
| 메모리 | 힙 공유 | 프로세스마다 별도 |

톰캣이 JVM 하나로 스레드 200개를 돌리는 것과, gunicorn이 프로세스
8개를 띄우는 것의 차이가 여기서 나온다.

## 백엔드 관점

- **요청 처리에 CPU 작업이 끼면 전체가 막힌다.** 이미지 리사이징, 큰 JSON
  파싱, PDF 생성 같은 건 별도 워커(Celery)로 뺀다.
- CPU 작업을 인라인으로 처리해야 한다면 `ProcessPoolExecutor`나
  `run_in_executor`로 밀어낸다 (25장).
- 외부 API 여러 개를 호출한다면 스레드나 asyncio로 병렬화한다.
  순차로 하면 대기 시간이 그대로 합산된다.
- **측정 없이 결정하지 않는다.** 스레드/프로세스 전환은 코드 구조를
  바꾸는 일이라, 실제로 빨라지는지 먼저 재본다.

## 실무 규칙

- 판단 순서: (1) IO/CPU 구분 → (2) CPU면 C 구현인지 확인 → (3) 실측
- `concurrent.futures`로 두 방식을 바꿔가며 재본다
- 프로세스는 작업 단위가 충분히 클 때만 이득이다
- 워커 수는 공식보다 **메모리 제약과 실측**이 우선이다
