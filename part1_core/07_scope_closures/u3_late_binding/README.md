# u3. 늦은 바인딩 — 루프에서 클로저를 만들면 생기는 일

## 지도 확인

u2에서 "클로저는 값이 아니라 변수(cell)를 캡처한다"를 봤고,
유제 3에서 로거 세 개가 전부 `[ERROR]`를 쓰는 걸 확인했다.
이번 유닛은 그 현상에 이름을 붙이고, 왜 파이썬이 이렇게 설계됐는지,
그리고 실무에서 어떻게 피하는지를 정리한다. 07장의 마지막 유닛이다.

## 개념 1 — 늦은 바인딩(late binding)이란

클로저가 캡처한 변수의 값을 **함수 정의 시점이 아니라 호출 시점에 읽는 것**.

```python
funcs = []
for i in range(3):
    funcs.append(lambda: i)

[f() for f in funcs]      # [2, 2, 2]  — 0,1,2가 아니다!
```

세 lambda가 전부 같은 `i` cell을 공유하고, 루프가 끝난 뒤 `i`는 2다.
호출 시점에 cell을 읽으니 전부 2가 나온다.

**이름의 의미**: 값이 "늦게"(호출 시점에) 결정된다는 뜻.
반대는 이른 바인딩(early binding) — 정의 시점에 값이 고정되는 것.

## 개념 2 — 원인은 두 가지가 겹친 것

**원인 1: `for`는 스코프를 만들지 않는다** (u1 개념 3)

```python
for i in range(3):
    pass
print(i)      # 2 — 루프 변수가 살아남는다
```

자바라면 루프 블록마다 새 변수지만, 파이썬은 함수 스코프라 `i`가 하나뿐이다.
변수가 하나면 **cell도 하나**다.

**원인 2: 클로저는 변수를 공유한다** (u2 개념 4)

값을 복사했다면 각 함수가 자기 값을 가졌겠지만, cell을 공유하니
마지막 값이 전부에게 보인다.

이 둘 중 하나만 달랐어도 이 함정은 없었다.

## 개념 3 — 언제 문제가 되고 언제 안 되나

**즉시 호출하면 문제없다.**

```python
for i in range(3):
    print((lambda: i)())      # 0, 1, 2 — 정상!
```

만들자마자 부르면 그 시점의 cell 값이 맞으니까. 문제는 **나중에 호출**할 때다.

**함정이 되는 전형적 상황**:
- 콜백/이벤트 핸들러를 루프에서 등록
- 스레드/태스크를 루프에서 생성
- 함수 리스트를 만들어 나중에 실행
- 데코레이터를 동적으로 생성

```python
# 실무에서 자주 보는 형태
handlers = {}
for event_type in ["click", "hover", "focus"]:
    handlers[event_type] = lambda e: log(f"{event_type}: {e}")
# 전부 "focus"로 로깅된다
```

## 개념 4 — 해결책 1: 기본값 인자 (이른 바인딩)

```python
funcs = []
for i in range(3):
    funcs.append(lambda i=i: i)     # 기본값으로 값을 고정

[f() for f in funcs]                # [0, 1, 2]
```

04장 u1에서 배운 "기본값은 `def`(또는 lambda) 실행 시점에 한 번 평가되어
`__defaults__`에 저장된다"를 이용한 것이다.

- 클로저 = cell 공유 = 늦은 바인딩
- 기본값 = 값 복사 = **이른 바인딩**

가변 기본값이 함정이었던 그 성질이 여기서는 **해법**이 된다.

`lambda i=i:`가 이상해 보이지만, 왼쪽 `i`는 매개변수 이름이고
오른쪽 `i`는 루프 변수다. 관용구로 굳어져 있다.

## 개념 5 — 해결책 2: 함수를 한 겹 더 (권장)

```python
def make_func(i):          # 호출마다 새 프레임 → 새 cell
    return lambda: i

funcs = [make_func(i) for i in range(3)]
[f() for f in funcs]       # [0, 1, 2]
```

**함수 호출이 스코프를 만든다**는 사실을 이용한다. `make_func`를 세 번
호출하면 프레임 세 개, `i` 세 개, cell 세 개다.

01장 u2의 `factory(2)`, `factory(3)`이 각자 cell을 가졌던 것과 같은 구조.

**이쪽이 더 명시적이다.** `lambda i=i:`는 트릭처럼 보이지만,
팩토리 함수는 "각 호출이 독립"이라는 의도가 코드에 드러난다.

## 개념 6 — 해결책 3: functools.partial

```python
from functools import partial

funcs = [partial(lambda i: i, i) for i in range(3)]
```

`partial`은 인자를 **미리 묶어두는** 도구다. 값이 그 시점에 고정되므로
이른 바인딩이 된다. 13장(함수 일급 객체)에서 정식으로 다룬다.

## 개념 7 — 컴프리헨션은 안전한가

```python
funcs = [lambda: i for i in range(3)]
[f() for f in funcs]        # [2, 2, 2] — 여전히 함정!
```

컴프리헨션이 자체 스코프를 갖긴 하지만(3.0+), **루프 변수는 여전히 하나**다.
컴프리헨션 안에서 한 번만 만들어져 재대입될 뿐이라 결과는 같다.

즉 컴프리헨션으로 바꿔도 해결되지 않는다. 위 세 해결책 중 하나를 써야 한다.

## 자바와 비교 — "자바는 이 함정이 없다"

자바는 두 가지 이유로 이 문제가 원천 차단된다.

```java
List<Runnable> funcs = new ArrayList<>();
for (int i = 0; i < 3; i++) {
    funcs.add(() -> System.out.println(i));   // 컴파일 에러!
}
```

1. **값 캡처**: 람다가 값을 복사하므로 애초에 공유가 없다
2. **effectively final 강제**: 캡처된 변수는 변경 불가라, `i++`로 바뀌는
   루프 변수는 캡처할 수 없다

향상된 for문(`for (String s : list)`)에서는 매 반복마다 `s`가 새 변수라
캡처가 가능하고, 각자 다른 값을 갖는다.

**즉 자바는 컴파일러가 막고, 파이썬은 조용히 통과시킨다.**
파이썬의 유연함이 여기서는 비용이 된다.

## 백엔드 관점

- **비동기 태스크 생성**에서 자주 터진다.
```python
  tasks = []
  for url in urls:
      tasks.append(asyncio.create_task(fetch(url)))   # 이건 안전 (즉시 인자 전달)
      tasks.append(asyncio.create_task(lambda: fetch(url)))  # 위험
```
  인자로 넘기면 안전하고, 클로저로 캡처하면 위험하다.
- 라우트/미들웨어를 동적 등록할 때, 스레드 풀에 작업을 넣을 때 같은 패턴.
- 증상이 "전부 마지막 값으로 동작"이라 **테스트에서 데이터가 하나면 안 잡힌다.**
  루프가 2회 이상 돌 때만 드러나는 버그다.

## 실무 규칙

- 루프 안에서 **나중에 실행될 함수**를 만들 땐 반드시 바인딩 시점을 확인한다.
- 기본 해법은 **팩토리 함수**(개념 5). 짧으면 `lambda x=x:`도 허용.
- 콜백에 값을 넘길 수 있으면 클로저 대신 **인자로 넘긴다**. 가장 안전하다.
